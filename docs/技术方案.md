# 墨屿 — 技术方案

> 品牌：墨屿（Moyu）  
> 版本：MVP v1.0  
> 配套文档：`docs/产品方案.md`  
> 原则：先简单可上线，再按需微服务化；云端 API 调用优先，自建模型后置

---

## 1. 设计目标与约束

### 1.1 目标

- 支持文生图、图生图、混元 / GPT 模型切换
- 支持积分预扣、失败退还、充值流水
- 生图异步化，前端可轮询任务状态
- MVP 可单人开发、低成本部署
- 后续可平滑拆出独立 AI Worker（Python）

### 1.2 约束

- MVP 阶段调用云端模型 API，不自建 GPU 推理
- 优先 TypeScript / Next.js 全栈，降低语言与部署成本
- 积分扣减必须事务一致，禁止「扣了分却无记录 / 有记录未扣分」
- 生成结果与用户上传图统一落对象存储

## 2. 架构选型策略

### 2.1 为什么可能用两种语言？

这不是炫技，而是专业分工：

| 角色 | 职责 | 擅长点 |
|------|------|--------|
| Next.js（Node.js） | 接待层：页面、鉴权、积分、支付回调、BFF | 高并发 Web、会话、SSR/CSR |
| Python（FastAPI Worker） | 干活层：模型 SDK、图像处理、未来自建推理 | AI 生态、SDK、GPU 工具链 |

生活类比：Next.js 是点单员和大堂经理；Python 是后厨大厨。非必要阶段，可以让「点单员直接打电话给云端中央厨房（混元/GPT API）」，不必自建后厨。

### 2.2 推荐演进路径

#### 阶段 A：MVP 简单版（推荐先做）

```
浏览器 → Next.js（页面 + API Routes）→ 混元 / GPT 云端 API
                ↓
         PostgreSQL + OSS
```

- 在 Next.js API Routes 内直接 `fetch` / SDK 调用模型
- 可用数据库任务表 + 轮询，或引入轻量队列
- **优点**：只学 TypeScript，部署简单（Vercel 等）
- **缺点**：若未来自建 SD / 复杂图像管线，仍需 Python

#### 阶段 B：成长版（用户量起来或需复杂处理时）

```
浏览器 → Next.js（BFF）→ Redis 队列 → Python FastAPI Worker → 混元/GPT/自建模型
                ↓                              ↓
           PostgreSQL                    对象存储 OSS/COS
```

- Next.js 管用户、积分、支付；Python 专管 AI 调用
- 队列解耦，便于重试、扩容、替换模型实现

**本文技术方案以阶段 B 为目标架构描述，同时标注阶段 A 的降本落地方式。**

## 3. 整体技术架构

### 3.1 逻辑架构图

```
┌─────────────────────────────────────────────────────────┐
│                      用户浏览器                          │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│              Next.js（前端 + API Routes / BFF）           │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐      │
│  │  页面渲染    │  │  用户认证    │  │  积分 / 支付 │      │
│  └─────────────┘  └─────────────┘  └─────────────┘      │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│              任务队列（Redis / BullMQ）                   │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│              Worker（Python FastAPI）                     │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐      │
│  │  混元 API    │  │  GPT API    │  │  结果上传 OSS │      │
│  └─────────────┘  └─────────────┘  └─────────────┘      │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│          PostgreSQL（主库） + 对象存储（OSS / COS）         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 数据流（一次生图）

1. 浏览器访问由 Next.js 渲染的站点  
2. 用户提交 Prompt（及可选参考图）→ Next.js API  
3. Next.js 校验登录与积分 → **预扣积分** → 写任务记录 → 入队 → 返回 `task_id`  
4. Worker 消费任务 → 调用混元 / GPT → 结果图上传 OSS → 更新任务状态  
5. 前端轮询 `/api/status/[id]` → 成功展示图片；失败则退还积分

## 4. 技术选型

| 层级 | 技术选型 | 理由 |
|------|----------|------|
| 前端 | Next.js（React + TypeScript） | 全栈框架，一套语言覆盖页面与 API |
| 后端 API | Next.js API Routes / Route Handlers | 与前端同仓，迭代快 |
| 任务队列 | Redis + BullMQ（或等价） | 轻量、可重试、易水平扩展 |
| AI Worker | Python FastAPI | AI SDK / 生态成熟；便于未来自建模型 |
| 数据库 | PostgreSQL | 事务强，适合积分扣减一致性 |
| ORM | Prisma（Next.js）/ SQLAlchemy（Python，可选） | 类型安全、迁移方便 |
| 对象存储 | 阿里云 OSS / 腾讯云 COS | 存上传图与生成结果 |
| 鉴权 | NextAuth / 自建 JWT Session | 与 Next.js 生态契合 |
| 支付 | 微信 / 支付宝（服务端回调） | 国内 C 端主流 |
| 部署 | Vercel（Next.js）+ 云主机（Worker） | 各取所长；MVP 也可全放一台机 |

### 4.1 MVP 降本选型（阶段 A）

| 项 | 建议 |
|----|------|
| 语言 | 仅 TypeScript |
| AI 调用 | Next.js API 内直接调混元 / GPT |
| 队列 | 可先同步调用 + 超时控制；或仅用 DB 状态字段 |
| Worker | 暂不部署 Python |
| 部署 | Vercel + 托管 PostgreSQL + OSS |

## 6. 数据库设计

### 6.1 users

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID PK | 用户 ID |
| email | VARCHAR(255) UNIQUE NOT NULL | 登录邮箱 |
| password | VARCHAR(255) NOT NULL | 哈希后的密码（若密码登录） |
| credits | INTEGER DEFAULT 10 | 当前积分余额 |
| created_at | TIMESTAMP | 创建时间 |

### 6.2 generation_tasks

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID PK | 任务 ID |
| user_id | UUID FK → users | 所属用户 |
| model | VARCHAR(20) | `hunyuan` / `gpt` |
| mode | VARCHAR(20) | `text_to_image` / `image_to_image` |
| prompt | TEXT | 用户提示词 |
| ref_image_url | VARCHAR(500) | 图生图参考图 URL |
| result_url | VARCHAR(500) | 生成结果 URL |
| cost | INTEGER | 本次消耗积分 |
| status | VARCHAR(20) | `pending` / `processing` / `done` / `failed` |
| error_message | TEXT NULL | 失败原因（对内） |
| created_at | TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMP | 更新时间 |

### 6.3 credit_transactions

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID PK | 流水 ID |
| user_id | UUID FK → users | 用户 |
| amount | INTEGER | 正数充值，负数消耗 / 退还可用正负约定一致 |
| type | VARCHAR(20) | `recharge` / `generation` / `refund` |
| description | VARCHAR(200) | 可读描述 |
| related_task_id | UUID NULL | 关联生图任务 |
| created_at | TIMESTAMP | 时间 |

### 6.4 （建议补充）recharge_orders

支付上线时建议增加订单表：订单号、金额、套餐、支付渠道、状态（pending/paid/closed）、第三方流水号、回调时间等，与积分入账一一对应，便于对账。

### 6.5 积分一致性要点

- 提交任务时：**同一事务**内完成「校验余额 → 扣减 credits → 写 credit_transactions → 写 generation_tasks」
- 任务失败时：**同一事务**内「退还 credits → 写 refund 流水 → 更新 task=failed」
- 禁止仅靠前端扣分；所有扣减在服务端完成
- 可选：对 `users.credits` 使用乐观锁（version）或 `UPDATE ... WHERE credits >= cost`

## 7. 核心业务流程

### 7.1 异步生图（推荐）

**步骤：**

1. **用户提交**  
   前端 → `POST /api/generate`  
   服务端：鉴权 → 算 cost → 预扣积分 → 创建任务 → 入队 → 返回 `task_id`

2. **Worker 处理**  
   取任务 → `status=processing` → 调模型 API → 上传 OSS → `status=done` + `result_url`  
   失败：标记 failed + 退积分 + 写 refund 流水

3. **结果获取**  
   前端轮询 `GET /api/status/[id]`（或后续改 SSE/WebSocket）  
   `done` 展示图片；`failed` 提示并刷新余额

### 7.2 关键设计点

| 设计 | 说明 |
|------|------|
| 预扣积分 | 防并发超卖；失败再退 |
| 异步解耦 | 生图耗时数秒到数十秒，避免 HTTP 长阻塞 |
| 重试 | 模型 API 瞬时失败指数退避重试；业务错误（违规）不重试 |
| 幂等 | 支付回调、退积分按订单/任务 ID 幂等处理 |
| 限流 | 用户级 QPS / 并发任务上限，防止成本打穿 |

### 7.3 阶段 A 同步简化版

若暂不引入队列：API 内直接调用模型（设合理 timeout），仍建议先写 task 记录与预扣逻辑，再更新结果；前端用 loading 态等待。流量上来后再切异步。

## 8. API 设计（草案）

### 8.1 认证

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/auth/register` | 注册，赠送体验积分 |
| POST | `/api/auth/login` | 登录 |
| POST | `/api/auth/logout` | 登出 |
| GET | `/api/auth/me` | 当前用户与余额 |

### 8.2 生图

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/generate` | 提交任务：model、mode、prompt、refImage（可选） |
| GET | `/api/status/[id]` | 查询任务状态与结果 |
| GET | `/api/history` | 分页历史作品 |

**POST /api/generate 请求示例：**

```json
{
  "model": "hunyuan",
  "mode": "text_to_image",
  "prompt": "一只可爱的橘猫坐在窗台上，柔和自然光",
  "refImageUrl": null
}
```

**响应示例：**

```json
{
  "taskId": "uuid",
  "cost": 2,
  "creditsLeft": 8,
  "status": "pending"
}
```

### 8.3 充值

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/recharge/packages` | 套餐列表 |
| POST | `/api/recharge/create` | 创建支付订单 |
| POST | `/api/recharge/webhook` | 支付渠道回调（验签 + 幂等入账） |
| GET | `/api/recharge/orders` | 用户订单列表 |

### 8.4 Worker 内部（阶段 B）

- 队列消息：`{ taskId, model, mode, prompt, refImageUrl, userId, cost }`
- Worker 只通过服务端凭证访问模型与 OSS；不暴露给浏览器
- 可选：Worker 回调 Next.js 内部 webhook 更新状态（或 Worker 直连同一 PostgreSQL）

## 9. 模型接入设计

### 9.1 统一抽象

对业务层屏蔽厂商差异，抽象为：

```
generateImage({ model, mode, prompt, refImageUrl, size }) → { imageUrl | buffer }
```

实现类：`HunyuanProvider`、`GptProvider`（Python 或 TypeScript 均可）。

### 9.2 混元

- 若兼容 OpenAI Image API 规范：替换 `base_url` + `api_key` 即可切换
- 注意：具体模型名、尺寸枚举、图生图参数以官方文档为准，接入时单独做适配层

### 9.3 GPT Image

- 使用 OpenAI 官方 SDK / HTTP API
- 与混元保持同一输出约定（最终统一为 OSS URL 再返回前端）

### 9.4 安全与密钥

- API Key 仅存服务端环境变量
- 禁止下发到浏览器
- 参考图与结果图建议私有读 + 签名 URL，或公共读但路径不可猜测

## 10. 对象存储与文件策略

| 类型 | 路径建议 | 说明 |
|------|----------|------|
| 用户上传参考图 | `uploads/{userId}/{uuid}.ext` | 上传后校验类型与大小 |
| 生成结果 | `results/{userId}/{taskId}.png` | 由 Worker 或 API 写入 |
| 访问方式 | 签名 URL / CDN | 控制盗链与流量成本 |

限制建议：单文件大小上限、仅允许 jpg/png/webp、病毒与内容安全可按阶段加强。

## 11. 安全、风控与可观测

### 11.1 安全

- 全站 HTTPS
- 密码哈希（bcrypt/argon2）
- 支付回调验签
- CSRF / CORS 按部署域名收敛
- 上传文件类型嗅探，不信任扩展名

### 11.2 风控

- 注册与生图频率限制
- 免费积分日上限
- 单用户并发任务数限制
- 异常高消耗告警（按日 API 成本）

### 11.3 可观测

- 结构化日志：taskId、userId、model、latency、status
- 关键指标：成功率、P95 耗时、队列堆积、积分退款次数
- 错误分类：模型 4xx（提示词/违规）vs 5xx（可重试）

## 13. 开发阶段与里程碑

| 阶段 | 周期 | 技术交付 |
|------|------|----------|
| Phase 1 | 1–2 周 | 用户体系 + 积分表 + 混元文生图（建议先阶段 A 直连） |
| Phase 2 | 1 周 | GPT + 模型切换 + 图生图 + OSS 上传 |
| Phase 3 | 1 周 | 支付下单/回调 + 历史列表 + 基础限流 |
| Phase 4 | 持续 | 异步队列化、Worker 拆分、监控告警、性能与成本优化 |

### 13.1 建议实施顺序（防踩坑）

1. 先打通「鉴权 + 积分事务 + 单模型出图」  
2. 再接 OSS 与历史  
3. 再接支付  
4. 最后再拆 Python Worker（真有必要时）

## 14. 技术风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 模型 API 超时 / 不稳定 | 体验差、退分增多 | 超时、重试、降级提示、多模型兜底 |
| 积分超卖 | 资损 | DB 事务 + 条件更新 |
| 支付重复回调 | 重复加积分 | 订单状态机 + 幂等键 |
| 存储与流量成本上升 | 毛利下降 | CDN、过期策略、压缩、签名链 |
| 过早微服务 | 研发与运维成本高 | MVP 坚持阶段 A，指标达标再拆 |

---

## 15. 总结

本技术方案采用 **「Next.js BFF +（可选）Python AI Worker」** 的演进式架构：

- **现在**：TypeScript 全栈直连混元 / GPT，最快验证产品与付费  
- **以后**：用 Redis 队列把生图抽到 Python，便于自建模型与复杂处理  

核心工程原则：**积分事务正确、生图异步可观测、密钥不出前端、架构可拆不可先拆。**

更细的 Prisma Schema、Worker 实现、支付对接可在编码阶段按模块单独展开。
