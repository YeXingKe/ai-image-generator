## 0. 先建立全局图（5 分钟）

### 0.1 一句话产品

**墨屿**是一个 **积分制 AI 生图网站**：用户注册 → 用文字（或参考图）生成图片 → 按次扣积分 → 积分不够就充值。

### 0.2 用奶茶店类比整套系统

| 现实里的奶茶店 | 墨屿系统 |
|----------------|----------|
| 顾客 | 浏览器里的用户 |
| 前台点单、收银 | **Next.js（frontend）**：页面 + API |
| 库存/会员余额本 | **PostgreSQL**：用户、积分、任务记录 |
| 中央厨房（外卖平台厨房） | **混元 / GPT 云端 API**（我们不自己养 GPU） |
| 后厨学徒（以后再招） | **Python Worker**（阶段 B 才认真上） |
| 冰箱里放成品图 | **对象存储 OSS/COS** |

**重要结论：**  
MVP 阶段可以「前台直接打电话给中央厨房」，**不必先会 Python**。  
Python 是留给「图像处理变复杂 / 要自建模型 / 任务很多要排队」时用的。

### 0.3 两个阶段（务必记住）

```text
阶段 A（现在优先）：
  浏览器 → Next.js（页面+API）→ 混元/GPT
                 ↓
          PostgreSQL +（可选）OSS

阶段 B（成长后再做）：
  浏览器 → Next.js（只做接待）→ Redis 队列 → Python Worker → 模型/OSS
                 ↓
            PostgreSQL
```

原则：**可拆不可先拆**。先验证「有人愿不愿意为出图付钱」，再拆微服务。

## 1. 业务分析

### 1.1 市场机会（为什么值得做）

- AI 生图已经从「好玩」变成「能嵌进日常出图」：头像、配图、商品图、海报草稿。  
- 大厂提供了现成 API（混元、GPT Image 等），小团队不必自建 GPU 机房。  
- 机会不在「再训一个最强模型」，而在：**好用的付费壳**——登录简单、扣费清楚、失败可退、能反复出图。

### 1.2 产品定位

| 项 | 内容 |
|----|------|
| 品牌 | 墨屿（Moyu） |
| 一句话 | 轻量 AI 生图工具：注册即用、按积分计费、多模型切换 |
| 目标用户 | 个人创作者、学生、小微电商/自媒体 |
| 不做（MVP） | 企业协作、节点工作流、自部署 SD、专业修图层 |

### 1.3 用户分层

| 用户 | 诉求 | MVP 是否重点 |
|------|------|----------------|
| C 端普通人 | 低门槛、好玩、头像/朋友圈图 | ✅ |
| 小微商家 | 商品图、海报、要快不要太贵 | ✅ |
| 设计师 | 灵感、草图、风格试错 | 部分覆盖 |

### 1.4 核心业务闭环（比功能列表更重要）

```text
注册/登录
   → 获赠体验积分（如 10 分）
   → 选模型（混元 / GPT）与模式（文生图 / 图生图）
   → 写提示词（图生图再上传参考图）
   → 点击生成：服务端预扣积分 → 异步出图
   → 成功：看图 / 下载；失败：自动退积分
   → 积分不足：引导充值 → 再出图
```

**商业验证的本质问题只有一句：**  
「用完免费积分后，有没有人愿意付钱再出图？」

### 1.5 收费与积分规则

#### 套餐（产品建议价）

| 套餐 | 价格 | 积分 | 说明 |
|------|------|------|------|
| 体验包 | 免费 | 10 | 注册赠送，控制刷量 |
| 基础包 | ¥9.9 | 50 | 入门付费 |
| 标准包 | ¥29.9 | 200 | 主力包 |
| 专业包 | ¥99 | 800 | 大客单、单价更低 |

#### 单次消耗

| 操作 | 积分 |
|------|------|
| 混元 · 文生图 | 2 |
| GPT · 文生图 | 3 |
| 图生图 | 在对应模型上 **再 +1** |

代码里费率见：`frontend/lib/credits.ts`、`frontend/lib/models.ts`。

#### 毛利底线（产品约束）

单次「积分折算售价」要能盖住：

1. 模型 API 成本  
2. 图片存储与流量  
3. 还要留一点毛利  

免费积分总量要可控，否则会被刷穿。

### 1.6 信息架构（用户看到的页面）

| 路由（现状） | 业务职责 |
|--------------|----------|
| `/` | 品牌落地页：登录/注册入口 |
| `/login` `/register` | 账户（当前为本地会话 mock，API 未真正接通） |
| `/workspace` | 生图工作台：左配置、右预览 |
| `/history` | 历史作品（需登录） |
| `/templates` `/gallery` | 占位「即将上线」 |
| `/about` | 品牌、商标、产品介绍 |

导航定义：`frontend/lib/nav.ts`。

### 1.7 生图任务状态机

```text
idle（未提交）
  → submitting（前端提交中）
  → pending（已入库，排队/等待）
  → processing（正在调模型）
  → done（有结果图）
     ↘ failed（失败，必须退积分）
```

前端要让用户「感觉有进度」，不能一直转圈没反馈。

### 1.8 风险与合规（业务侧）

| 风险 | 应对思路 |
|------|----------|
| 违规内容 | 依赖模型方安全策略 + 保留任务日志 |
| 刷免费积分 | 注册校验、IP/设备限流、日上限 |
| 支付纠纷 | 订单可查、积分流水可对账 |
| API 成本失控 | **预扣积分** + 并发/频率限制 |
| 预期过高 | 文案说明 AI 有随机性，支持重试 |

### 1.9 MVP 成功指标

| 指标 | 含义 |
|------|------|
| 注册转化 | 访问 → 注册 |
| 首次出图率 | 注册后至少成功 1 次出图 |
| 付费转化率 | 用完免费分 → 充值（**核心**） |
| 次日留存 | 第二天还回来吗 |
| 失败率 | failed / 总任务 |
| API 毛利率 | （收入 − API/存储）/ 收入 |

### 1.10 产品路线图（简版）

1. **Phase 1**：注册登录 + 积分 + 混元文生图 → 跑通闭环  
2. **Phase 2**：GPT + 图生图 + 模型切换  
3. **Phase 3**：真实支付 + 历史优化  
4. **Phase 4**：体验、风控、留存  
5. **以后**：模板市场、批量、超分；需要时再上 **Python Worker**

## 3. 核心数据设计（实现细节）

数据库用 **PostgreSQL**，前端侧用 **Prisma** 描述表结构（见 `frontend/prisma/schema.prisma`）。

### 3.1 三张核心表

#### （1）users — 用户与余额

| 字段 | 含义 |
|------|------|
| id | 用户主键 |
| email | 登录邮箱（唯一） |
| password | **哈希后**的密码（绝不明文） |
| credits | 当前积分余额（注册默认 10） |
| created_at | 注册时间 |

#### （2）generation_tasks — 每一次生图

| 字段 | 含义 |
|------|------|
| id | 任务 ID（前端轮询用） |
| user_id | 谁发起的 |
| model | `hunyuan` / `gpt` 等 |
| mode | `text_to_image` / `image_to_image` |
| prompt | 提示词 |
| ref_image_url | 参考图（可空） |
| result_url | 结果图 URL（可空） |
| cost | 本次扣了多少积分 |
| status | pending / processing / done / failed |
| error_message | 失败原因（对内） |

#### （3）credit_transactions — 积分流水（对账本）

| 字段 | 含义 |
|------|------|
| amount | 变动值（建议：充值/退还为正，消耗为负，团队内约定一致即可） |
| type | `recharge` / `generation` / `refund` |
| related_task_id | 关联哪次生图（可空） |
| description | 给人看的说明 |

支付上线后建议再加 **recharge_orders（充值订单表）**，方便和微信/支付宝对账。

### 3.2 积分一致性（比「会不会调 API」更重要）

**铁律：积分只在服务端改，且和流水、任务写在同一事务里。**

提交生成时（同一事务）：

1. 查余额是否 ≥ cost  
2. `credits -= cost`  
3. 写一条 `generation` 流水  
4. 写一条 `generation_tasks`（status=pending）  

失败时（同一事务）：

1. `credits += cost`（退还）  
2. 写 `refund` 流水  
3. 任务改为 `failed`  

错误示范：

- 只改前端显示的积分  
- 扣了分却没写流水  
- 失败了不退分  

可用：`UPDATE users SET credits = credits - $cost WHERE id = $id AND credits >= $cost`，影响行数为 0 则说明余额不足。

## 4. 一次生图：端到端实现流程

### 4.1 推荐：异步流程（目标）

```text
1. 浏览器 POST /api/generate
      body: { model, mode, prompt, refImageUrl?, modelVersion?, size? }

2. Next.js API（服务端）
      - 校验登录
      - 用 credits 规则算 cost
      - 事务：预扣积分 + 写流水 + 创建 task
      - 阶段 A：自己调模型 或 后台继续跑
      - 阶段 B：把 taskId 丢进 Redis 队列
      - 立即返回 { taskId, cost, creditsLeft, status: "pending" }

3. Worker / 后台任务
      - status → processing
      - 调用混元或 GPT Provider
      - 图片上传 OSS，得到 result_url
      - status → done；失败则退积分

4. 浏览器轮询 GET /api/status/[id]
      - pending/processing → 继续转圈
      - done → 展示图片
      - failed → 提示错误并刷新余额
```

### 4.2 阶段 A 同步简化版（可先实现）

没有 Redis/Python 时：

- 在 `POST /api/generate` 里 **直接 await 调模型**（设好超时）  
- 仍然要：**先落库任务 + 预扣**，再更新结果  
- 前端用 loading；并发上来后再改异步  

### 4.3 Provider 抽象（实现时别写死厂商）

业务代码不要到处写「腾讯 URL / OpenAI URL」，而要：

```text
generate(task) → Provider 接口
                  ├─ HunyuanProvider
                  └─ GptProvider
```

仓库占位：

- 前端侧：`frontend/lib/providers/`  
- Python 侧：`worker/app/providers/`（`base.py` / `hunyuan.py` / `gpt.py`）

这样换模型或加第三个厂商时，只加适配器，不改积分与任务主流程。

### 4.4 密钥与安全（小白必记）

| 可以 | 不可以 |
|------|--------|
| 密钥放服务器环境变量（`.env`，且不提交 git） | 把模型 Key 写进前端 React 代码 |
| 服务端 Route Handler / Worker 调 API | 浏览器直接拿 Key 调混元/GPT |
| 支付回调验签 | 信任前端传来的「我已付款」 |

## 6. Python Worker：小白实现指南（阶段 B）

即使你现在只学 Python，也建议先理解下面结构，避免「上来就堆脚本」。

### 6.1 现有骨架在做什么

| 文件 | 作用 |
|------|------|
| `worker/app/main.py` | FastAPI 应用入口，挂健康检查 |
| `worker/app/routers/health.py` | `GET /health` 之类探活 |
| `worker/app/worker.py` | 预留「死循环消费队列」入口（尚未接 Redis） |
| `worker/app/providers/*` | 各模型适配器占位 |
| `worker/app/services/storage.py` | 上传 OSS 占位 |
| `worker/app/config.py` | 读环境变量 |

本地启动（见根目录 README）：

```bash
cd worker
python -m venv .venv
# Windows:
.venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

打开 `http://localhost:8000/docs` 可看 FastAPI 自动文档。

### 6.2 Worker 理想工作循环（伪代码）

```python
# 概念示意，不是当前可运行完整实现
while True:
    job = queue.fetch()          # 从 Redis 取一条任务
    if not job:
        sleep(短暂时间)
        continue
    mark_task_processing(job.task_id)
    try:
        image_bytes = provider.generate(job)
        url = oss.upload(image_bytes)
        mark_task_done(job.task_id, url)
    except BusinessError as e:    # 如内容违规：不重试
        refund_and_fail(job, e)
    except TransientError:        # 网络抖动：有限次重试
        requeue_with_backoff(job)
```

### 6.3 你作为 Python 小白的学习路径（贴合本项目）

| 顺序 | 学什么 | 和本项目的关系 |
|------|--------|----------------|
| 1 | 变量、函数、类型注解、`venv`、`pip` | 能跑起 `worker` |
| 2 | `httpx`/`requests` 调 HTTPS JSON API | 将来调混元/GPT |
| 3 | FastAPI：路由、Pydantic 模型 | 读懂 `main.py`，加内部接口 |
| 4 | 读环境变量、不把密钥写进代码 | `config.py` |
| 5 | 文件/字节上传到 OSS SDK | `services/storage.py` |
| 6 | Redis 列表/队列基础 | 接 `worker.py` 消费循环 |
| 7 | （可选）异步 `async/await` | 提高 Worker 吞吐 |

**不必一上来学**深度学习训练、CUDA、微服务治理——MVP 用的是**别人的模型 API**。

### 6.4 阶段 A 时 Python 同学能干什么？

即使主链路在 Next.js，你仍可：

1. 把某个模型调用先用 **Python 小脚本**验证通（本地实验）  
2. 把成功经验迁到 `worker/app/providers/xxx.py`  
3. 用 FastAPI 做「内部调试接口」（仅本机或内网）  
4. 等产品要拆队列时，脚本逻辑几乎可原样搬进 Worker

## 7. Next.js 架构详解（先分清：不是 NestJS）

> 名字只差一个字母，非常容易混：  
> - **Next.js**（本仓库在用）：React 全栈框架，既能画页面，也能写 API。  
> - **NestJS**：偏后端的 Node 框架，像「TypeScript 版的 Spring」，主要做 API，一般不负责整站页面。  
> **墨屿项目 = Next.js，没有用 NestJS。**

### 7.1 一张表分清两者

| | Next.js（本项目） | NestJS（本项目没有） |
|--|-------------------|----------------------|
| 主要用途 | 网站页面 + 顺手写后端接口 | 纯后端服务 / 微服务 |
| 你写什么 | React 页面 + `route.ts` API | Controller / Service / Module |
| 类比 | 前台柜台 + 小后仓（一个店） | 只有中央厨房，店面另找 |
| 目录习惯 | `app/page.tsx`、`app/api/...` | `src/users/users.controller.ts` |
| 和 Python 类比 | 有点像「Django 既能出页又能出 API」 | 更像「只要 API 的 FastAPI 项目」 |

### 7.2 Next.js 在墨屿里到底干什么？

一句话：**一个 `frontend/` 文件夹，同时干两件事。**

```text
用户打开网站
    │
    ├─ 要「看得见的页面」？
    │     → app/login/page.tsx、app/workspace/page.tsx …
    │     → 浏览器里渲染 React UI（按钮、表单、工作台）
    │
    └─ 要「看不见的接口」？
          → app/api/generate/route.ts、app/api/auth/login/route.ts …
          → 跑在服务器上：查库、扣积分、调模型（密钥不能给浏览器）
```

这就是文档里说的 **BFF（Backend For Frontend）**：  
后端不是另一个独立大项目，而是 **嵌在 Next.js 里的 `/api/*`**，专门服务这个前端。

### 7.3 用文件夹地图理解（对照真实仓库）

```text
frontend/
├── app/                          ← Next.js「App Router」根
│   ├── layout.tsx                ← 所有页面共用外壳（字体、标题）
│   ├── page.tsx                  ← 路由 `/` 首页
│   ├── login/page.tsx            ← 路由 `/login`
│   ├── workspace/page.tsx        ← 路由 `/workspace`
│   ├── about/page.tsx            ← 路由 `/about`
│   │
│   └── api/                      ← 这里开始是「后端接口」，不是页面
│       ├── auth/login/route.ts   → POST /api/auth/login
│       ├── generate/route.ts     → POST /api/generate
│       └── status/[id]/route.ts → GET  /api/status/某id
│
├── components/                   ← 拼装 UI 的积木（工作台、导航、品牌）
├── lib/                          ← 业务工具：算积分、Prisma、校验
└── prisma/schema.prisma          ← 数据库表定义
```

**记忆口诀：**

- 路径里有 `page.tsx` → 给人看的网页  
- 路径里有 `api/.../route.ts` → 给程序调用的接口  
- 文件夹名字 ≈ URL：`app/login/page.tsx` → `/login`

### 7.4 请求怎么走？（工作台点「生成」）

```text
① 浏览器里的 GenerateWorkspace（React 组件）
      │  fetch("/api/generate", { method: "POST", body: ... })
      ▼
② Next.js 服务器执行 app/api/generate/route.ts
      │  （这里可以：鉴权、扣积分、写数据库、调混元）
      ▼
③ 返回 JSON 给浏览器
      │  { taskId, status, ... }
      ▼
④ 组件根据结果更新右侧预览 / 提示错误
```

注意：① 和 ④ 在**用户电脑浏览器**里跑；② 在**你的服务器（或本机 `pnpm dev`）**里跑。  
所以模型 API Key 只能出现在 ②，不能写进 ① 的组件代码。

### 7.5 「客户端组件」和「服务端组件」是啥？

Next.js 默认很多文件可以在服务端渲染。若文件第一行写了：

```ts
"use client";
```

表示：**这个文件要在浏览器里交互**（`useState`、点击、localStorage 等）。

本项目例子：

| 文件 | 有无 `"use client"` | 原因 |
|------|---------------------|------|
| `workspace/page.tsx` | 有 | 要用 AuthGate、会话 |
| `generate-workspace.tsx` | 有 | 表单状态、点按钮 |
| `api/generate/route.ts` | 无（也不需要） | 本身就是服务端 API |

Python 类比：`"use client"` ≈ 「这段必须跑在用户浏览器」；`route.ts` ≈ 「这段像 FastAPI 的一个路由函数」。

### 7.6 和「传统前后端分离」对比

| 传统分两仓 | 墨屿现在（Next.js 全栈 MVP） |
|------------|------------------------------|
| `web/` React 前端 + `server/` NestJS/FastAPI | 只有 `frontend/`（页面+API）+ 以后可选 `worker/` |
| 前端 `localhost:3000`，后端 `localhost:8000` | 页面和 `/api` 通常同一个端口（如 3000） |
| 跨域、两套部署 | MVP 部署简单，一个人好维护 |

阶段 B 才会再加 **Python Worker**（真正的「第二个后端进程」），那时 Next.js 仍负责页面和积分，Python 专管生图队列。

### 7.7 工作台数据流（UI 已实现的部分）

`GenerateWorkspace`（`frontend/components/generate/generate-workspace.tsx`）：

1. 选模型系列与版本  
2. 选文生图 / 图生图、画幅、提示词  
3. 展示预计消耗积分（`calcGenerationCost`）  
4. `fetch('/api/generate', …)` —— 目前后端多为 501，属预期  

### 7.8 鉴权现状 vs 目标

| | 现状 | 目标 |
|--|------|------|
| 会话 | `localStorage` 客户端会话 | HttpOnly Cookie / JWT，服务端校验 |
| 保护路由 | `AuthGate` 看本地会话 | API 每层校验 userId |
| 积分展示 | 会话里缓存的数字 | 以 `/api/auth/me` 与流水为准 |

## 8. 部署与成本（实现时心里有数）

### 8.1 MVP 推荐部署

| 组件 | 建议 |
|------|------|
| Next.js | Vercel 或一台云主机 Node |
| PostgreSQL | 托管数据库（或 Docker） |
| OSS/COS | 云厂商对象存储 |
| Python Worker | 暂不部署；阶段 B 再上小规格云主机 |
| Redis | 阶段 B 再开（`docker compose --profile worker`） |

### 8.2 成本粗估维度

- 模型 API：按张计，是大头  
- 存储与 CDN 流量：结果图累积后变明显  
- 服务器：MVP 可很低  
- 支付手续费：充值时计入  

产品侧用「积分售价 > 成本」约束技术选型，避免用最贵模型却卖最便宜的包。

## 10. 关键设计决策速查

| 问题 | 决策 |
|------|------|
| 要不要一上来微服务？ | 不要，先阶段 A |
| 积分在哪扣？ | 只在服务端，事务 + 流水 |
| 生图为什么异步？ | 几秒～几十秒，别卡死 HTTP |
| 为什么预扣？ | 防并发超卖；失败再退 |
| Key 放哪？ | 仅服务端环境变量 |
| Python 何时必上？ | 复杂图像管线 / 自建模型 / 队列扩容时 |
| MVP 成功看什么？ | 付费转化，不是模型榜单第一 |

## 11. 名词表（Python 小白向）

| 名词 | 通俗解释 |
|------|----------|
| SaaS | 软件不用安装，开网站就能用，按订阅或按次付费 |
| MVP | 最小可行产品：用最少功能验证有没有人买单 |
| BFF | Backend For Frontend：专门给前端用的后端层 |
| API | 程序之间约定好的「请求/响应」接口 |
| 事务 | 一捆数据库操作：要么全成功，要么全撤销 |
| 预扣 | 先扣钱（积分），事办不成再退 |
| 幂等 | 同一请求执行多次，结果和一次一样 |
| Provider | 适配器：把「不同厂商的生图 API」收成统一调用方式 |
| OSS | 对象存储：专门存图片文件的云盘 |
| 队列 | 任务排队：生产者丢任务，消费者一个个做 |
| FastAPI | Python 里写 HTTP 服务的流行框架 |
| Prisma | TypeScript 侧操作数据库的 ORM |
| 轮询 | 前端每隔 N 秒问一次「好了没」 |

## 13. 总结

墨屿的商业本质是：**用积分把「云端生图 API」包装成可感知、可付费、可复购的产品**。  

技术本质是：**Next.js 管人与钱与任务状态；模型算力租云端；Python Worker 是成长后的专业后厨，不是开学第一课。**  

对你这个 Python 小白最稳的路径是：

> 先理解业务闭环与积分事务 → 用脚本验证模型 API → 再进入仓库里的 FastAPI Worker 骨架 → 最后在阶段 B 接上队列。

功能做减法，商业做闭环，技术留扩展口——先活下来，再长出来。
